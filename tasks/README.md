# 任务看板 · 协作协议

> 本目录是仓库的**共享任务看板**：任务发布者把「思想」拆成可落地的任务，**每个任务一个
> Markdown 文件**发布到本目录；执行 AI 领取后完成，完成后删除该任务文件。
>
> **角色划分（先读这段，防止角色错位）：**
> - **发布者**：使用者**唯一指定**的任务发布专用会话。只有它能发布任务、维护本协议、
>   汇报看板状态；它不执行任务、不碰项目代码。
> - **执行者**：**其余所有 AI 会话**——无论你在自己会话里是什么角色（编排者、专家、
>   子 Agent 都算）。AGENTS.md 里「主 Agent」专指**本项目的发起者**（账号 `2333up` 本人），
>   跟某个会话里的编排者无关，**更不等于你是发布者**。在本看板上你只有四个动作：
>   **领取 → 执行 → 完成/阻塞**。发现新需求时，写进相关任务的「问题记录」区或告知使用者，
>   由发布者拆解发布。
>
> 它和 `AGENTS.md` 分工不同、互不冲突：**AGENTS.md 管「谁有权限做什么」**，
> **本看板管「当前有哪些活、谁在做、做完了没有」**。

---

## 一、目录结构：一任务一文件

```
tasks/
├── README.md             本协议 + 基本约束清单（唯一入口）
├── T-001-精简首页中心描述.md    任务 1
├── T-002-xxx.md         任务 2
└── ...
```

- 每个任务一个文件，文件名 = `T-编号-简短标题.md`，编号递增、删除后不回收复用。
- 任务状态记在**文件内的头部元信息**里，不看文件名。
- 看「当前有哪些活」= 直接看 `tasks/` 目录里的文件列表。

## 二、任务有哪几种状态

| 状态 | 含义 |
|---|---|
| `open` | 待认领。任务已发布，等任何 AI 来领。 |
| `in-progress` | 进行中。已被某 AI 认领，**其他人不得再动这个任务**。 |
| `blocked` | 阻塞。认领后发现卡点（缺依赖、等别人、信息不足），写明原因后挂起，**不删除**。 |

## 三、任务的生命周期

```
发布 open ──> 认领 in-progress ──> 完成（删除文件）
                     │
                     └──> 阻塞 blocked ──> 解除后回到 open / in-progress
```

### 1. 发布（仅发布者可做，执行者不得发布）
发布者把「思想」拆成一个个独立可验收的任务，**每个任务新建一个文件**，状态 `open`、
认领者留空。**只发「需要跨会话、需要别人接」的活**；自己当场能做完的不必上板。然后单独 commit
（`chore(tasks): 发布任务 T-xxx`）。

**执行者无权新建任务文件。** 你发现新需求时：写进相关任务的「问题记录」区，
或告知使用者，由发布者统一拆解发布。

### 2. 领取（执行者做）
开工前**先 `git pull` 拉最新，再看一遍 `tasks/` 目录**。认领时：
- 把该任务文件头部状态从 `open` 改成 `in-progress`，认领者写自己（会话角色名）；
- **先单独 commit 这次认领**（`chore(tasks): 认领 T-xxx`），再开始写代码。

这样能防止两个 AI 同时领同一个任务互相撞车。

### 3. 完成（执行者做）
验收标准全部勾选、跑通 AGENTS.md 第 6 节自检后：
- **把该任务文件整个删除**（`git rm tasks/T-xxx.md`）；
- commit（按 Conventional Commits，`feat`/`fix`/`docs` 等，见 AGENTS.md 第 3 节）。

### 4. 阻塞（执行者做）
卡住时把状态改成 `blocked`，在「备注」里写清「卡在哪、需要谁/什么才能继续」，
commit 后**保留文件，不删除**。解除后改回 `open` 或 `in-progress`。

## 四、任务文件格式

每个任务文件固定用下面的骨架，字段缺一不可：

```markdown
---
id: T-001
状态: open
认领者: （留空 = 待认领）
优先级: P1
创建: 2026-10-18
---

# T-001 一句话标题

## 目标
一句话说清要交付什么。

## 验收标准
- [ ] 明确可勾选的验收点 1
- [ ] 明确可勾选的验收点 2

## 约束条件
- **基本约束**（全局，见 README「基本约束清单」）：自动适用。
- **本任务约束**：针对本任务的额外限制。

## 范围 / 红线
涉及哪些文件/接口；若属 AGENTS.md §0.1「重大修改」，须先提方案。

## 备注
背景、依赖、上下文链接等。

## 问题记录（执行 Agent 回写）
- [日期] 执行中产生的问题 → 供发布者提炼新基本约束。
```

- **优先级**：`P0` 紧急 / `P1` 高 / `P2` 普通 / `P3` 低。
- **认领者**：写清楚是哪个会话/角色（如「后端子 Agent」「前端子 Agent」），避免歧义。

## 五、基本约束清单（全局，每个任务自动适用）

> 这些约束**对每个任务都生效**，发布任务时不必重复写，执行 Agent 必须遵守。
> 清单**只增不减**：发现新的、会反复出现的问题，就追加进来。

1. **减少不必要的内容生成。** 只做任务明确要求的东西：
   - UI 文案能短则短，不写「产品自我介绍」式的长说明段；
   - 不加没被要求的页面元素、弹窗、注释、文档、测试文件；
   - 不私自扩大需求范围（「顺手」多做的功能一律不做）。
2. **会话结束时回写问题。** 执行 Agent 在**每次会话结束（或任务完成）时**，把本次
   执行过程中产生的问题、踩坑、卡点，写进它正在执行/已完成任务文件的「问题记录」区。
   发布者据此发现 Agent 执行中反复出现的问题，从而**提炼成新的基本约束**，避免同类错误再犯。

## 六、必须遵守的红线

1. **角色不越位（最重要）**：只有发布者可新建任务文件、修改本协议、汇报看板状态。
   其余所有 AI 会话一律是执行者——**无论你在自己会话里是不是编排者**——
   在本看板上只有「领取 / 执行 / 完成 / 阻塞」四个动作，不得发布任务、不得替使用者做需求决策。
2. **开工前必读**：先 `git pull`，再看 `tasks/` 目录。看不到这条 = 可能领到已被别人
   认领的活。
3. **认领先落笔**：改状态、写认领者，**先 commit 再动手**，不许先写代码后补状态。
4. **完成即删除**：任务文件整个删掉，不要留着改成「已完成」堆积。
5. **阻塞要写清原因**，不删文件、不假装完成。
6. **一个 commit 只做一件事**：发布/认领/完成各自单独 commit，不和其他代码混在一起。
7. **遵守 AGENTS.md 的推送红线**：push 权限按 AGENTS.md §0 执行；与发布者身份无关。
8. **会话结束前必回写问题**（见基本约束第 2 条），否则发布者无法迭代约束清单。
